# REST API Theory Notes

## 왜 REST API를 배우는가

백엔드의 가장 기본 역할은 요청을 받고, 처리하고, 응답을 돌려주는 것이다.

REST API는 이 흐름을 가장 단순하게 보여주는 방식이라서, 백엔드 입문자가 가장 먼저 익히기 좋다.

이 문서의 목적은 아래 세 가지다.

1. REST API의 핵심 개념을 정리한다.
2. 실습 코드에 나오는 용어를 다시 찾아볼 수 있게 한다.
3. 수업 후에도 README에서 연결된 이론 문서로 복습할 수 있게 한다.

---

## 핵심 용어 정리

### Resource

Resource는 API가 다루는 대상이다.

예를 들어 이 레포에서는 `아이돌(Idol)` 정보가 Resource다.

REST에서는 보통 Resource를 URI에 명사 형태로 표현한다.

좋은 예:

- `/idols`
- `/idols/1`

나쁜 예:

- `/getIdols`
- `/createIdol`

### URI

URI는 자원을 식별하는 주소다.

REST에서는 "무엇을 다루는지"를 URI로 표현하고, "무슨 행동을 하는지"는 HTTP Method로 구분한다.

### HTTP Method

HTTP Method는 요청의 목적을 나타낸다.

| Method | 의미 | 예시 |
|------|------|------|
| `GET` | 조회 | 전체 목록 조회, 단건 조회 |
| `POST` | 생성 | 새 데이터 생성 |
| `PUT` | 수정 | 기존 데이터 수정 |
| `DELETE` | 삭제 | 기존 데이터 삭제 |

### Request Body

Request Body는 클라이언트가 서버에 보내는 데이터 본문이다.

예를 들어 아이돌 생성 요청은 아래처럼 JSON 형태로 전달할 수 있다.

```json
{
  "name": "카리나",
  "group": "aespa",
  "agency": "SM",
  "debutYear": 2020
}
```

### Response

Response는 서버가 클라이언트에 돌려주는 결과다.

보통 아래 두 가지를 함께 본다.

- 응답 본문
- HTTP 상태 코드

### Status Code

Status Code는 요청 결과를 숫자로 표현한다.

| 코드 | 의미 | 언제 쓰는가 |
|------|------|------------|
| `200 OK` | 성공 | 조회, 수정 성공 |
| `201 Created` | 생성 성공 | POST 요청 성공 |
| `204 No Content` | 성공, 본문 없음 | 삭제 성공 |
| `400 Bad Request` | 잘못된 요청 | 요청 데이터가 잘못됨 |
| `404 Not Found` | 대상 없음 | 없는 id 조회 |
| `500 Internal Server Error` | 서버 오류 | 예상 못한 실패 |

## 왜 Controller와 Service를 나누는가

입문자가 가장 많이 헷갈리는 부분 중 하나는 "왜 굳이 파일을 나누는가"다.

이 레포에서는 아래 기준으로 역할을 나눈다.

### Controller

Controller는 요청과 응답을 다루는 창구다.

주요 역할:

- URL 받기
- PathVariable, RequestBody 읽기
- Service 호출
- 응답 반환

즉, "입구" 역할에 가깝다.

### Service

Service는 실제 비즈니스 로직이 있는 곳이다.

주요 역할:

- 데이터 찾기
- 데이터 생성/수정/삭제
- 예외 상황 처리
- 필요하면 DTO로 변환

즉, "처리" 역할에 가깝다.

### 왜 나누는가

Controller에 모든 코드를 몰아넣으면:

- 코드가 길어지고
- 테스트가 어려워지고
- 다음 주차에서 DB나 보안이 붙을 때 구조가 무너진다.

그래서 입문 단계부터 역할 분리를 습관처럼 가져가는 것이 좋다.

---

## DTO는 왜 쓰는가

DTO는 데이터를 주고받기 위한 객체다.

이 레포에는 두 가지가 있다.

- `IdolRequest`
- `IdolResponse`

### 왜 Request DTO를 쓰는가

클라이언트가 보낸 JSON을 서버 내부 모델에 바로 꽂아 넣지 않고, "입력 형식"으로 한 번 받기 위해 사용한다.

장점:

- 검증하기 쉽다
- 어떤 값을 입력받을지 명확하다
- 내부 모델과 입력 형식을 분리할 수 있다

### 왜 Response DTO를 쓰는가

서버 내부 데이터 구조를 그대로 노출하지 않고, "응답으로 보여줄 형식"을 따로 정리하기 위해 사용한다.

장점:

- 응답 형태를 통제할 수 있다
- 내부 필드를 숨길 수 있다
- 나중에 구조가 바뀌어도 대응이 쉽다

---

## Validation은 왜 필요한가

입문 단계에서도 "잘못된 입력을 막는 감각"은 중요하다.

예를 들어:

- 이름이 비어 있으면 안 된다
- 데뷔 연도가 너무 비정상적이면 안 된다

그래서 `@NotBlank`, `@Min` 같은 검증 어노테이션을 붙인다.

이 검증은 나중에 더 복잡한 입력 처리로 확장될 때 중요한 기초가 된다.

## 현재 레포가 메모리 기반인 이유

이 레포는 DB가 아니라 메모리 리스트를 사용한다.

이유는 단순하다.

13주차의 목표는 DB를 배우는 것이 아니라, "요청 -> 처리 -> 응답" 흐름을 먼저 이해하는 것이기 때문이다.

메모리 기반 구조의 특징:

- 빠르게 시작할 수 있다
- 구조 이해에 집중할 수 있다
- 서버를 재시작하면 데이터가 사라진다

이 한계가 바로 다음 단계에서 DB를 배우는 이유가 된다.

## 이 실습을 통해 가져가야 하는 것

이 레포의 핵심은 CRUD 자체보다 아래 흐름을 이해하는 데 있다.

1. 클라이언트가 요청을 보낸다.
2. Controller가 요청을 받는다.
3. Service가 실제 처리를 한다.
4. Response DTO로 응답을 만든다.
5. 상태 코드와 함께 결과를 돌려준다.

이 흐름을 이해하면, 이후 DB, 인증, 테스트, 배포도 결국 이 구조 위에서 확장된다는 점이 보이기 시작한다.
